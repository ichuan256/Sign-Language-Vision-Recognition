# 运行中熄屏：异常复位及恢复 · 2026-10-31

> 历史单目候选的一次异常复位及恢复，不用于判断后续三栏故障根因。后续含音频候选的彩条、静态三栏和实时视觉已通过实屏确认。本文的“当前”均指该次诊断时点；最近部署及进程状态看[统一入口](../../../docs/当前状态.md)。

用户报告运行中屏幕熄灭，并明确说明没有断电或按复位。此前用户已确认单目分屏正常，新原始画面与识别帧号持续更新。

## 确认的事实

- 旧启动周期 `e76d7158-8738-4d79-bed8-18bba720d2d4` 已结束；检查时为新周期 `114765b1-3d7b-452b-aad0-4260abbcb947`，新启动单调时间约236秒。
- 原输出 owner PID22262 和绘制 PID23312 均不存在。旧日志止于采集约1264秒（约21分钟）、完整帧10596、显示缓冲更新11484，未产生正常退出的 `report.json` / `results.json`。电脑端报 `OV5640 frame truncated`。
- 相机与输出程序的3600秒上限尚未到达。旧文件中的 `active=true` 是重启前遗留状态，不能当作当前进程存活证据。
- 当前启动的固件标记、bit/hwh SHA、PYNQ硬件元数据及FCLK0=100MHz均通过核验。恢复前相机DMA和HDMI VDMA均为Halted，bootpy服务正常完成。
- 只读复位状态寄存器 `SLCR.REBOOT_STATUS (0xF8000258)` 得到 `0x00400000`，只有bit22 POR标志。

## 原因判断和限制

熄屏的直接原因是板卡进入了新的启动周期，原HDMI输出进程和采集进程随整机复位消失；重启后只冷加载固件，不会自动恢复此前Python显示会话。

[AMD复位原因说明](https://docs.amd.com/r/en-US/52030/Solution?contentId=KAWa6AiaUBmsxIRIR8m4JA)定义bit22为Power-On Reset。当前标志与上电复位相符，结合用户未操作，优先检查5V供电瞬断、压降、供电线及插头接触；**未实测电压，不能据此确定具体供电故障点或宣称电源适配器损坏**。这些状态位也有软件可写及跨非POR复位保留的语义，需保留原始值而非过度解释。

pstore为空；上一启动的kernel journal读取超时，当前启动dmesg未提供上一次异常的确定原因。不能将“没读到panic”写成“已排除内核异常/看门狗”。板端实时时钟与电脑日期有偏差，本次判断依据boot ID和单调时钟，不用板端文件墙钟推算准确断电时间。

## 当次恢复记录

安全核对新启动中的固件与DMA停机后，将旧电脑控制台切到idle，正常刷新该空闲服务并加载已有owner自动启动/复用代码，再启动 `single_hdmi`。新输出owner PID9911，启动周期与当前标记一致。用户确认：“已恢复，帧号增加”。

当次没有请求重启板卡、没有修改启动项、没有在线加载位流、没有修改模型或训练。恢复后保留了当时的输出和采集运行。当时控制台已加载此前延迟加载的owner自动启动/复用增量；其创建新owner的路径在该次新启动恢复中通过实际出图验收。上述PID及运行状态不代表最近会话。

证据：`dark_diagnostic.json`、`reset_reason.json`、`dark_recovery.json`。前一轮 `live_verification.json` 与 `owner_preserved.json` 保留为上一启动的成功记录，不覆盖历史owner身份。
