# 单手关键点第二阶段：整层调度与融合

**第二阶段首轮加速已上板：单 ROI 前向从 12.276 秒降至 1.863 秒，约 6.59 倍加速。**
同一 ROI 三次运行的 64 输出均与整数参考逐值一致，模型权重和量化尺度未变，没有 CPU 神经网络回退。
当前约 0.54 ROI/s，**尚未达到 5Hz 阶段目标**，也不是连续视频端到端帧率。
对比基线为 [首版上板记录](single_hand_board.md)。
结构化实测与新 bit/hwh 哈希见 [single_hand_acceleration.json](single_hand_acceleration.json)。
HDMI 显示本轮实际 PL 输出与 1.863 秒耗时，用户已明确确认骨架和耗时正常；这是静态 ROI 验收。

## 本轮 PS / PL 分工

PS 负责图调度、输入复制、缓存维护和结果解码；固定权重/bias/移位参数在初始化时打包到 DDR 常驻，逐层直接引用物理偏移；普通卷积、专用 depthwise、全连接及可融合的
ReLU 在 PL 执行。其余残差、池化、均值和 presence 仍用原 vector 核，没有 CPU 神经网络回退。

`kp_layer` 每次处理完整一层 NHWC 张量，不再由 PS 展开 im2col、拼接小 GEMM 结果。
普通卷积每输出通道块加载一次权重、复用于全部空间位置；depthwise 直接按通道计算，不再乘稀疏零值。
独占消费者的相邻 ReLU 与卷积融合，但严格保留“卷积舍入/饱和→ReLU 截断→再次舍入/饱和”边界。
被残差等其他分支同时使用的卷积输出不能直接覆盖，规划器会拒绝这种融合。

49 个计算层输出使用独立的 DDR/CMA 缓冲区（合计 8749568 字节），后继卷积可直接引用物理地址；
保留各分支缓冲区，避免覆盖残差输入。返回的是共享视图，CPU 若需要读取则先按有效范围失效缓存，
不再复制每个卷积输出。残差/池化等 vector 边界仍经过 PS 复制，不宣称整网硬件流水。
缓存刷新/失效改用有效张量范围；已只读核对板端 PYNQ 切片的偏移、长度及生命周期实现。

## 已完成验证

| 项目 | 结果 |
|---|---|
| 7 ROI 整网 HLS C 对整数参考 | 全部逐值一致，最大差 0 |
| 每 ROI 发起次数 | 5893 → **115**，其中 49 次整层计算、66 次 vector |
| 独立层核整数向量 | 7 组、724 输出、0 LSB |
| 层核 XSim C/RTL | PASS，含 3×3 卷积、5×5 depthwise、stride 2、17 通道尾块、672 输入通道、融合舍入 |
| HLS 估计资源 | LUT 21737、FF 19788、DSP 61、BRAM18K 23；不是整板布线资源 |
| 软件回归 | 154 项通过，32 个 subtest 通过，2 条既有 protobuf 警告 |
| 实际 PL 对齐 | 1 个独立 ROI、进程内重复 3 次，每次 64 输出均 0 差异 |
| 整板实现 | LUT 35913/53200（67.51%）、DSP 157/220（71.36%）、BRAM Tile 59/140 |
| 实际时序/路由 | WNS 0.234ns、WHS 0.011ns，TNS/THS=0；76987 条可布线网络全部完成，0 路由错误 |

PC 上 HLS C 的耗时不是 FPGA 推理延迟；调用数下降也不等于等比例加速。
HLS 的普通卷积输入通道循环实际 II=2，不能仍按理想 II=1 承诺帧率。
5Hz 仍是目标，必须以板端前向和最终端到端延迟验收。

首次 RTL 仿真适配器因测试指针只分配了小向量、未覆盖接口声明深度而越界，未进入板端。
测试缓冲区补足 AXI 声明深度后，重新执行 CSim/综合/RTL 仿真并导出 IP；失败日志保留。

本轮初始化约 14.300 秒，只在进程启动时发生；必须保持模型和驱动常驻。
SSH 请求总计 25.313 秒包含初始化、3 次前向及进程开销，不能当成单次推理。
仅 1 个独立 ROI，3 次重复的均值 1.866 秒；不构成独立视频评测或长期稳定性验收。

首轮细分计时：输入复制/刷新 0.028534 秒、层启动/等待 1.497103 秒、输出失效/视图 0.016633 秒、
vector 调用合计 0.251895 秒。启动/等待包含 PS 寄存器访问和轮询，不能直接称纯 PL 运算时间。
36/49 个层输入直接复用 DDR 地址，单次前向仅复制 662816 字节输入；固定权重常驻 DDR。

主要瓶颈已转为 depthwise 的短 DDR 读取和普通卷积；不能只继续减少 PS 调用，或承诺仅靠提频达到 5Hz。
下一轮优先做片上输入行/块缓存，减少邻域重复读取；再检查普通卷积 II=2 的反馈路径，
以及 vector 残差/池化的串行循环。仍需 C/RTL、整板时序、同条件板端对齐和延迟门禁。

## 连续视频修正与验收

首轮 HDMI 入口 `show_hand_result.py` 是固定 ROI 数值验收，只显示单帧，不能作为动态回放演示。
用户指出后新增 `vision.keypoints.dynamic_pl` 和板端常驻 `stream_hand_board.py`：
录制视频按时钟连续循环，PC 发布目标 15fps；单独线程向同一个常驻 PL 网络提交最新 ROI，
仅保留一个待处理输入，过期请求被替换，不让推理阻塞视频或堆积长队列。
无需重新下载 bit，也不修改启动项。

已由用户目视确认“视频运动，帧号和 PL 编号都在变化”；
实际动态输入与输出 SHA 均有多种值，观测快照见 [dynamic_replay.json](dynamic_replay.json)。
视频＋HDMI 并发时，PL 前向约 1.97 秒；这与独立测试约 1.86 秒分开记录。
每个 ROI 经传输 SHA 核验，结果记录保留源帧号、源时间和实际核调用数，无 CPU 网络回退。

此入口目前使用同一已核对 SHA 的片段及其已有 PC 手部 ROI 轨迹，**不是任意视频自主检测**。
主画面把最近一次 PL 手指姿态映射到当前 PC ROI，因此位置/旋转来自 PC ROI 跟踪，手指姿态有延迟；
右侧显示最近一次实际 PL 输入及输出，画面明确标注源帧和 pose age。没有将缓存 PC 指关节直接当作 PL 输出绘制。
PC 发布速率、HDMI 实际刷新率、PL 姿态更新率必须分开，不能只报“15fps 实时”。

本次演示有界运行 600 秒，结束后 HDMI 保留最后一帧。观测 JSON 是快照，不表示进程永久运行。
实时完整日志在 `project/_tmp/kp_dynamic_pl_v1/`；运行结束后生成最终 `report.json`。
新增连续链路及二进制分帧/最新请求队列测试后，最终回归 156 项通过，32 个 subtest 通过，仍为 2 条既有警告。
