# 视频模拟摄像头 → 关键点叠加 → HDMI（2026-10-25）

当前需求为**单目 OV5640**，硬件未到货，只预留帧源接口。
本次输入是已录视频，PC 做关键点检测与叠加，经 SSH/JPEG 回传板卡现有 HDMI 帧缓冲。
未做语义分类、未重载 bitstream、未改板卡/Windows 启动项。

## 实际验收经过

1. 板卡冷启动后 `bootpy.service=exited`、FPGA 状态 operating；核对 bit/hwh
   同时匹配 `build_manifest_20261023_btngpio.json`，远端显示/接收脚本也与仓库一致。
2. 当时没有显示缓冲所有者，启动默认 `download=False` 的 `hdmi_display.py`，PID 2679。
3. 首次接收只设 60 秒：日志确认至少 300 次写屏，327 次 JPEG 请求（包括连接探测），
   帧地址保持 `0x15c00000`，无断连记录。结束后保留最后一帧。
4. 用户随后反馈“只是一帧画面”。只读复核发现接收进程已按时退出，显示所有者仍活着。
   因而撤回过早的“连续播放通过”判断，增加可见 FRAME/SOURCE 计数，恢复 600 秒播放。
5. 恢复后两次本地状态相隔约 2 秒：帧号 866→907，取帧请求 152→165。
   用户进一步明确确认：**“帧号持续变化，视频正常运动”**；此前已确认骨架叠加正常。

因此通过的是“录制视频时钟回放、骨架叠加、网络回传、HDMI 持续运动”功能链路，
不是 OV5640 实采、30fps HDMI 显示、关键点定位精度或无人值守长期稳定性验收。

## PC 回放样本与计时

- 源视频 SHA256：`e5757f56a24a777d59256c047a4d84967dd527a912f17d558da572e50619d217`。
- 原尺寸 352×288，源 20fps；不按词义参与任何计算，仅使用媒体像素。
- 120 秒回放记录：2399 处理/发布帧，19.99fps；迟到丢弃 2 帧，完成 42 次循环。
- 主机 read→结果 P50/P95：46.49/47.69ms；包含源节拍等待，不含编码/显示实际呈现延迟。
- 60 秒链路日志只有每 100 次写屏计数，不能推算精确 HDMI 显示 FPS；请求吞吐约 5 次/秒量级，
  与 PC 20fps 不同，当前没有宣称全链路 20/30fps。

本机完整运行证据在 `project/_tmp/keypoints/hdmi_session_20261025_02/` 与
`hdmi_session_20261025_03/`，其中 03 是较长播放；本地日志不入库。
用户的显示确认另存 [confirmation.json](confirmation.json)，不伪造接收程序能测到肉眼状态。
